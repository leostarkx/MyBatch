# خطة الانتقال المعماري إلى Cloud SQL PostgreSQL وضمان ترحيل كافة البيانات دون أي فقدان 🏛️🐘

تهدف هذه الخطة الهندسية إلى حل مشكلة نفاد حصة القراءة المجانية في Firestore (التي تتجاوز 50,000 عملية قراءة يومياً وتسبب توقف التطبيق) عبر الانتقال الجذري والآمن إلى **قاعدة بيانات علائقية متطورة Cloud SQL (PostgreSQL Developer Edition)**، مع **أتمتة سحب وترحيل 100% من البيانات الحالية من Firestore إلى PostgreSQL** دون ضياع أي ملف أو سجل أو حساب طالب.

---

## 1. تشخيص المشكلة الحالية ولماذا PostgreSQL هو الحل الأمثل

### أسباب القفزة الهائلة في قراءات Firestore الحالية:
1. **طبيعة قواعد NoSQL Document Store**:
   - كل مستند في Firestore يُحسب كـ "عملية قراءة (Read Unit)". عند فتح صفحة الطلاب أو الحضور أو الدرجات لدفعة فيها 50 طالباً مع موادهم وامتحاناتهم وسجل غياباتهم، يقوم Firestore بتحميل كل وثيقة وسجل على حدة.
   - الاستماع الحي (`onSnapshot`) في المحادثات الجماعية، الإشعارات، والمهام يعيد احتساب قراءة كل وثيقة تتغير لجميع المستخدمين المتصلين في نفس اللحظة.
   - بمجرد دخول 7 مستخدمين وتنقلهم بين الأقسام، تتضاعف القراءات لتصل إلى عشرات الآلاف في ساعات معدودة، مما يؤدي للوصول للحد اليومي المجاني (50,000 قراءة) وتوقف الخدمة بخطأ: `Quota limit exceeded`.

### مزايا الانتقال إلى Cloud SQL PostgreSQL:
1. **استعلامات SQL موحدة (No Per-Read Billable Unit)**:
   - استعلام واحد مثل `SELECT * FROM grades WHERE batch_id = $1` يجلب مئات السجلات كعملية استعلام واحدة متكاملة دون احتساب "قراءة لكل صف".
   - ربط الجداول بواسطة `JOIN` لجلب بيانات الطالب ومواده ودرجاته في كويري واحد فائق السرعة.
2. **سعة وتحمل هائل مجاني مع Developer Edition**:
   - توفير بيئة PostgreSQL سحابية تتضمن إمكانية تقليص الموارد عند الخمول (Scale-to-zero) لتوفير التكاليف مع أداء فائق ومجاني للاستخدام الأكاديمي.
3. **حفظ وتكامل البيانات (ACID Transactions & Foreign Keys)**:
   - منع تكرار البيانات أو حذف سجلات مرتبطة بالخطأ، مما يضمن دقة كشوفات السعي والغيابات بنسبة 100%.
4. **الاحتفاظ بنظام تسجيل الدخول (Firebase Auth)**:
   - سيبقى تسجيل الدخول بالبريد الجامعي / الباسورد عبر Firebase Auth كما هو، بينما تنتقل قاعدة البيانات إلى PostgreSQL، مما يعني أن المستخدمين لن يحتاجوا لإعادة إنشاء حساباتهم.

## 2. البنية المعمارية للنظام الجديد (Architecture & Stack)

```
┌────────────────────────────────────────────────────────────────────────┐
│                        React SPA Frontend (Vite)                       │
│    (واجهات المستخدم: الرئيسية، المركز الدراسي، المسار، والمجتمع)      │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                         HTTP / REST API Requests
                         (مع Firebase ID Token)
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                   Full-Stack Express Server (server.ts)                │
│  - تحقق آمن من الـ Tokens وصلاحيات الممثل والطالب (Auth Middleware)    │
│  - مسارات API (/api/batches, /api/grades, /api/attendance, /api/chat...)│
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                             Drizzle ORM
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                     Cloud SQL PostgreSQL Database                      │
│     (جداول علائقية منظمة، فهارس سريعة، قيود تكامل، وترحيل آمن)         │
└────────────────────────────────────────────────────────────────────────┘
```

### التقنيات المعتمدة:
- **قاعدة البيانات**: Google Cloud SQL (PostgreSQL).
- **طبقة الـ ORM**: Drizzle ORM (`drizzle-orm`, `drizzle-kit`, `pg`).
- **خادم الـ API**: Node.js + Express (`server.ts` مدمج مع Vite Middleware في وضع التطوير).
- **المصادقة (Authentication)**: Firebase Auth (سلس وآمن، مع التحقق من الهوية على الخادم).

## 3. مخطط الجداول في PostgreSQL (Drizzle Database Schema)

سيتم إنشاء الجداول التالية في `src/db/schema.ts` لتعكس جميع هياكل البيانات الحالية وتفوقها في الأداء:

1. **`users`**: معرف الطالب (`id` يطابق Firebase UID)، الاسم، البريد، الدور (`student`, `representative`, `admin`)، القسم، المرحلة، ونوع الدراسة.
2. **`batches`**: الدفعات الجامعية، رمز الدفعة (`batch_code`)، رقم الـ PIN، ومعرف الممثل.
3. **`courses`**: المواد الدراسية، اسم الدكتور، الساعات، والفصل الدراسي.
4. **`schedules`**: الجدول الأسبوعي، الأيام، التوقيت، القاعات، والكروبات.
5. **`announcements`**: التبليغات الرسمية، التثبيت، والناشر.
6. **`assignments`**: الواجبات، تواريخ التسليم، الكروبات المستهدفة، وحالة إنجاز الطلاب.
7. **`exams`**: جدول الامتحانات والكويزات والمادة والملاحظات.
8. **`grades`**: سجلات السعي التفصيلية (الكويزات، المد، العملي، السعي من 50).
9. **`attendance_sessions`**: جلسات الحضور (التاريخ، المادة، الكروب).
10. **`attendance_records`**: تفاصيل حضور وغياب كل طالب لكل جلسة.
11. **`chat_messages`**: شات الدفعة الجماعي مع الردود والصور.
12. **`materials` & `material_sections`**: الملازم والمحاضرات وبنوك الأسئلة.
13. **`student_summaries`**: الملخصات المكتوبة بالمحرر المرئي والشروحات.
14. **`batch_suggestions`**: صندوق مقترحات الدفعة والتصويتات والردود.
15. **`notifications`**: إشعارات الطلاب الشخصية والجماعية.
16. **`join_requests`**: طلبات الانضمام للدفعة وقبول الممثل لها.

## 4. استراتيجية ترحيل البيانات المؤتمتة (Zero-Data-Loss Migration)

لضمان عدم ضياع أي معلومة نهائياً، ستتم عملية الترحيل وفق 4 مراحل دقيقة:

### الخطوة 1: أخذ نسخة احتياطية محلية كاملة (Snapshot Backup)
- إنشاء سكريبت سحب تلقائي `scripts/export-firestore-backup.ts` يتصل بقاعدة Firestore الحالية (`ai-studio-b1a98069-6ad1-4ecb-8502-4c49c2b777af`).
- تصدير كافة المجموعات والوثائق إلى ملف JSON محلي آمن ومفهرس (`backup-firestore-data.json`).

### الخطوة 2: إنشاء جداول Cloud SQL وتطبيق الهيكلية (Drizzle Migration)
- تهيئة وتجهيز جداول PostgreSQL عبر `drizzle-kit push`.
- التحقق من جاهزية العلاقات والفهارس (Foreign Keys & Primary Keys).

### الخطوة 3: استيراد البيانات إلى PostgreSQL (Data Import & Transformation)
- سكريبت مؤتمت `scripts/import-to-postgres.ts` يقوم بقراءة النسخة الاحتياطية وإدخال البيانات في PostgreSQL بالترتيب الصحيح لضمان سلامة العلاقات:
  1. إدخال الدفعات (`batches`).
  2. إدخال المستخدمين والطلاب (`users`).
  3. إدخال المواد والجدول (`courses`, `schedules`).
  4. إدخال السجلات (الدرجات، الحضور، المهام، التبليغات، الشات، الملخصات).
- مطابقة أعداد السجلات بين النسخة الأصلية وقاعدة PostgreSQL للتأكد من اكتمال الترحيل بنسبة 100%.

### الخطوة 4: تشغيل واجهات API والتحويل السلس
- توفير خدمات الاستعلام عبر مسارات Express `/api/*`.
- تعديل دوال الواجهة الأمامية (`services/api.ts`) لتتصل بالخادم وتستلم البيانات فوراً دون استهلاك أي حصة قراءة من Firestore.

## 5. خطوات التنفيذ التقنية (Step-by-Step Execution Plan)

### المرحلة الأولى: تهيئة Cloud SQL والحصول على الموافقة
1. استدعاء فحص الأهلية `CheckFeatureEligibility` عبر `rpc_action`.
2. إظهار واجهة الموافقة للمستخدم `show_aistudio_ui` مع `cloudsql_setup`.
3. استدعاء `CreateInstance` لإنشاء قاعدة بيانات PostgreSQL Developer Edition.

### المرحلة الثانية: إعداد المكتبات والخادم المحلي
1. تثبيت الحزم المطلوبة: `drizzle-orm`, `drizzle-kit`, `pg`, `@types/pg`, `express`, `@types/express`, `tsx`.
2. إعداد ملف الاتصال `src/db/index.ts` وقواعد البيانات `src/db/schema.ts`.
3. إنشاء ملف خادم Express المدمج `server.ts` وتحديث سكربتات التشغيل في `package.json` (`"dev": "tsx server.ts"`, `"start": "node server.ts"`).

### المرحلة الثالثة: سحب البيانات وترحيلها التلقائي
1. كتابة وتشغيل سكريبت سحب البيانات من Firestore والاحتفاظ بنسخة JSON.
2. ترحيل السجلات بالكامل إلى PostgreSQL مع التحقق من مطابقة الأرقام والسجلات.

### المرحلة الرابعة: ربط واجهات المنصة واختبارها
1. استبدال دوال استدعاء Firestore في `services/` بمستدعي API خفيف وسريع.
2. فحص جميع شاشات المنصة (الرئيسية، المهام، كشوفات السعي، الحضور والغياب، والمحرر).
3. فحص البناء النهائي عبر `compile_applet` و `lint_applet`.

## 6. خطة التحقق والضمان (Verification & Safety)

1. **التحقق من سلامة البيانات**:
   - مطابقة عدد الطلاب، المواد، الدرجات، وجلسات الحضور المسجلة قبل وبعد الترحيل.
2. **التحقق من كفاءة الاستعلامات**:
   - التأكد من استجابة استعلامات الجداول في أقل من 50ms دون أي حدود للقراءة.
3. **الحفاظ على صلاحيات الوصول**:
   - التحقق من بقاء صلاحيات الممثل والطلاب كما هي ومطابقتها لحساباتهم السابقة.
4. **انعدام الأخطاء نهائياً**:
   - اختفاء أخطاء `Quota limit exceeded` للأبد وتمتع المنصة باستقرار كامل وسرعة فائقة.
